# UX Critic

A design review tool. Drop in a screenshot of a screen you designed: code measures contrast and sizes from the pixels, Claude evaluates the screen against named UX principles, and every note is marked on the screenshot. You can push back on any note and compare versions over time. There is no overall score: progress is shown as fixed, still open and new issues.

## The two modes

Same screens, same components, different data source (`docs/10-demo-mode.md`). Every screen reads and writes through one `DataClient` interface, so no screen knows where its data comes from.

| | Demo | Live |
|---|---|---|
| Where | Online on Vercel, or locally | Only on your laptop |
| Turned on by | `UXC_MODE=demo`, or no `UXC_MODE` at all | `UXC_MODE=live` in `.env.local` |
| Data | Sample projects from `demo/data.json` and `public/demo/*.png` | SQLite in `data/uxcritic.db`, screenshots in `data/screenshots/` (both gitignored) |
| Your changes (push back, checklist, delete) | Saved only in your own browser (`localStorage`) | Saved in the database |
| New review | Pick a sample screen and watch its prepared review | Upload any screenshot, real measuring and evaluation |
| Claude API | Never called, no key, no API routes in the build | Called with your own key, from the server only |

The demo always shows a Demo pill and where its sample reviews came from ("written by hand", or "generated by Claude on <date>" after `pnpm demo:build`). The states you can't reach in the demo (Connect Claude, Review failed, Evaluation unreadable) are shown with sample data under `/states`.

## Setup

You need Node 24 and pnpm 12.

```bash
pnpm install
```

### Run the demo

```bash
pnpm dev
```

Open http://localhost:3000. Without `UXC_MODE=live` the app always runs as the demo.

As the production build, the way Vercel serves it:

```bash
UXC_MODE=demo pnpm vercel-build && UXC_MODE=demo pnpm start
```

`vercel-build` runs `next build` and then `scripts/check-demo-build.ts`, which fails the build if it finds an API route, the database, the review pipeline, the Claude SDK, or an API key in the environment.

### Run live mode

Live mode runs only on your laptop. Screenshots go to the Claude API and nowhere else: no analytics, no telemetry, no other third party requests. Text recognition (tesseract.js) runs locally with its language data from npm.

1. Create `.env.local` (gitignored, see `.env.example`):

   ```
   UXC_MODE=live
   ANTHROPIC_API_KEY=your-key-here
   ```

   Optional: `UXC_MODEL` (default `claude-sonnet-5-5`), `UXC_TIMEOUT_MS` (default 60000), and `UXC_PRICE_INPUT_PER_M` / `UXC_PRICE_OUTPUT_PER_M` in euros for the spend line on My checklist
2. `pnpm db:migrate` (optional: the app also creates and updates the database when it starts)
3. `pnpm dev` and open http://localhost:3000

Without a key, live mode shows Connect Claude. From there you can continue with measured checks only: contrast and text size still run, target sizes and the evaluation are skipped, and the review says so. `UXC_FAKE_AI=1` answers both Claude calls from fixtures (`lib/fake-ai.ts`) instead of calling Claude; the live Playwright tests use it. After changing `lib/db/schema.ts`, run `pnpm db:generate` and commit the new migration in `lib/db/migrations/`.

## How a review works

A live review runs four steps (`docs/03-review-pipeline.md`); the Reviewing screen shows each one as it happens.

1. **Prepare.** sharp stores the upload as PNG and makes the image for Claude (long edge at most 2576 px). Boxes Claude returns are scaled back to the original pixels.
2. **Measure.** tesseract.js finds the text lines. Claude call 1 finds the controls (buttons, links, inputs), but only where they are: code then measures every text line for contrast and text size, and every control for target size, from the pixels (`docs/04-measured-checks.md`). Every check is saved, pass or fail, and failures become measured notes. All of this is saved **before** the evaluation starts, so a failed evaluation never loses it.
3. **Evaluate.** Claude call 2 gets the screenshot, your context, the principles you turned on, your own rules and the failing measurements. It answers in a JSON schema (`output_config.format`), which is validated again with zod: unknown principles, empty text and boxes outside the image are dropped, at most 8 notes are kept. A timeout or network error fails the review (measured notes kept, Try again). An answer the app can't read makes the review partial (Evaluation unreadable, Retry evaluation).
4. **Place.** Boxes go back to original pixels, evaluated duplicates of measured problems are dropped, and notes are numbered in reading order. Regions are approximate, and the Review screen says so.

Compare matches the notes of two versions by principle and region overlap (or a similar title) and shows what was fixed, what is still open and what is new (`docs/07-compare.md`).

## Measured vs evaluated

| | Measured | Evaluated |
|---|---|---|
| Who decides | Code, from the pixels | Claude, against a named principle |
| What | Text contrast (WCAG 1.4.3), target size (WCAG 2.5.8 and the 44 px rule), body text size (the 16 px rule) | Everything that needs an opinion: labels, hierarchy, errors, choices, consistency |
| Shown as | "Measured", the value and threshold, "Measured from pixels" | "Evaluated", "Based on <principle>", confidence high, medium or low |
| Can be wrong because | OCR misses or splits a line; a control is located in the wrong place | Claude misreads the screen, or reports something that isn't a problem |

Only values computed by code are labelled Measured. Every evaluated note names its principle from `docs/05-principles.md` or one of your own rules.

## Evaluation

Tests prove the code works. The evaluation measures how good the reviews are (`docs/08-testing-and-evaluation.md`). The cases are the 12 fixture pages in `eval/fixtures/` (three fictional products: a coffee shop, a fitness app and a logistics tool), each with planted problems in `<name>.expected.json`. Two of them are clean, to count false alarms.

| Command | Key needed | What it does |
|---|---|---|
| `pnpm eval:capture` | no | Renders every fixture at 1280 × 800, scale 2, to `eval/cases/<name>.png` and `<name>.json` (planted problems with boxes, plus the page's controls) |
| `pnpm eval:measured` | no | Scores only contrast and text size on every case (real OCR and pixel measuring, no Claude call) with the same matcher. Writes `eval/runs/<date>-measured.md` with found, missed and unexpected per case and in total |
| `pnpm eval` | yes | Runs the full pipeline (both Claude calls) on every case, 3 times each, and writes the report |
| `pnpm eval --report eval/runs/<date>.results.json` | no | Makes the report again after you marked unexpected notes |
| `pnpm demo:build` | yes, live mode | Captures the demo screens, runs the real pipeline on each and writes `demo/data.json` with `source: "claude"` and the date |

How `pnpm eval` scores: results are matched to the planted problems with the same matcher as Compare. A matched problem is **found**, an unmatched one **missed**, and a note that matches nothing is **unexpected**. Unexpected is not automatically wrong: the report lists each one, you mark it `"real"` or `"invented"` in `eval/runs/<date>.review.json`, and `pnpm eval --report …` counts them. The report (`eval/runs/<date>.md`) has the model, per case and total found, missed and unexpected, recall, the spread over the 3 runs, measured vs evaluated, time and tokens per review, and the list of unexpected notes. Numbers are never copied into the app or the docs automatically.

A full `pnpm eval` makes 72 Claude calls (12 cases × 3 runs × 2 calls). Try one case first: `pnpm eval --case login --runs 1`. Without a key, `UXC_FAKE_AI=1 pnpm eval` runs the whole harness on fixture answers; its files are named `-fake-ai` and the report says its numbers mean nothing. `pnpm demo:build` refuses to write fake answers into `demo/data.json` (use `--out <file>`).

You can add your own cases: a PNG and a JSON in `eval/cases/` with the same shape (`lib/eval/case.ts`), without `controls`. `eval/runs/` is gitignored.

> **Honest note.** The evaluated half of UX Critic has not been scored yet. `pnpm eval` and `pnpm demo:build` have only been run in fake AI mode, because no API key was used while building this. Only contrast and text size have real numbers (`pnpm eval:measured`, no key needed); target size needs Claude call 1 and is not scored yet. The demo's evaluated notes are written by hand from the planted problems until `pnpm demo:build` is run with a key.

## Tests

| Command | What it checks |
|---|---|
| `pnpm test` | unit tests (contrast, measuring, OCR cleaning, parsing and validation, placing, compare, scoring and the report) |
| `pnpm test:e2e` | every screen flow with axe: in demo mode, in live mode with fake AI (own database in `.e2e-data/`), and live without a key |
| `pnpm test:smoke` | the production build in demo mode: every screen with axe, no third party requests, API paths 404, robots, og:image |
| `pnpm lint`, `pnpm typecheck`, `pnpm build` | ESLint and Prettier, TypeScript strict, the Next.js build |

No test calls Claude. `pnpm demo:og` recaptures the og:image (`app/opengraph-image.png`) from a running demo build: `node scripts/og-capture.ts http://localhost:3000`.

## Deploy the demo to Vercel

1. Import the GitHub repository in Vercel (framework preset: Next.js, root directory: the repository root)
2. Set exactly these environment variables for Production and Preview: `UXC_MODE=demo` and `ENABLE_EXPERIMENTAL_COREPACK=1` (so Vercel uses the pnpm version in `package.json`)
3. Never add `ANTHROPIC_API_KEY` to Vercel. A demo build with a key fails on purpose
4. Deploy. Vercel runs `pnpm install` and `pnpm vercel-build`

## How this repository was built

The spec in `docs/` was built milestone by milestone with Claude Code (`docs/09-milestones.md`); what was built and every decision made along the way is in `docs/CHANGELOG.md`.

* `CLAUDE.md` rules Claude Code reads automatically
* `docs/` the full spec, in reading order 00 to 10 (10 explains demo and live mode)
* `design/` the 15 screens as images, and `design/source/` the same screens as HTML for exact spacing and copy

Sample data in the designs (Checkout practice, NeighborGoods, FashionFlock, all numbers) is only for the mockups. The demo uses its own sample projects from docs/10.
