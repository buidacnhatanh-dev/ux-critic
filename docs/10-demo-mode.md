# 10 · Demo mode and live mode

UX Critic has two modes. Same screens, same components, different data source.

| | Demo mode | Live mode |
|---|---|---|
| Where | Online on Vercel (public link for the portfolio), also locally | Only on the owner's laptop |
| Turned on by | `UXC_MODE=demo` (Vercel always sets this), or no `UXC_MODE` at all | `UXC_MODE=live` in `.env.local`, plus a key (without one, Connect Claude, docs/03) |
| Data | Built in sample projects from `demo/data.json` and `public/demo/*.png` | SQLite in `data/` |
| Visitor changes (push back, checklist, delete) | Saved in the visitor's browser (`localStorage`), never on a server | Saved in the database |
| New review | Pick a sample screen, watch the steps, get its prepared review | Upload any screenshot, real measuring and evaluation |
| Claude API | Never called | Called |

**Hard rule:** the public deployment never has an API key and never calls Claude. Live mode only runs locally.

## One interface, two clients

All screens get data through one interface, `lib/data/client.ts`:

```ts
interface DataClient {
  mode: "demo" | "live";
  listProjects(): Promise<ProjectSummary[]>;
  getProject(id: string): Promise<ProjectDetail>;
  getReview(id: string): Promise<ReviewDetail>;          // includes status, issues, measurements
  startReview(input: StartReviewInput): Promise<{ reviewId: string }>;
  retryEvaluation(reviewId: string): Promise<void>;
  setPushback(issueId: string, reason: string | null): Promise<void>;
  deleteProject(id: string): Promise<void>;
  getChecklist(): Promise<Checklist>;
  saveChecklist(update: ChecklistUpdate): Promise<void>;
  resetDemo?(): Promise<void>;                            // demo only
}
```

* `DemoClient` (browser): loads `demo/data.json` once, applies the visitor's changes stored in `localStorage` under `uxc-demo-v1`, and writes changes back there. Wrap every `localStorage` call in try/catch; if storage is blocked, changes last until reload
* `LiveClient` (browser): calls the API routes from docs/01, which use SQLite and the pipeline
* `useDataClient()` returns the right one based on the mode, which the root layout reads on the server and passes down
* In demo mode, every API route except static files returns 404, and the code never opens the database or imports the pipeline. Check this with a test
* The API route files are named `route.live.ts`. `next.config.ts` only adds the `live.ts` page extension when `UXC_MODE=live`, so a demo build contains no API routes at all, and `scripts/check-demo-build.ts` fails if one appears

Interview note for the owner: this is the "repository pattern". The screens do not know where data comes from.

## Demo data

`demo/data.json` follows the same types as the live data (docs/02) plus a `source` field per review:

* `"handwritten"`: written by Claude Code from the planted problems in the eval fixtures, for building the app
* `"claude"`: produced by the real pipeline with `pnpm demo:build` (below), with the date

The demo badge shows which one: "Demo · sample reviews written by hand" or "Demo · reviews generated by Claude on 3 Nov 2026".

Sample projects (screens come from `eval/fixtures/*.html`, captured to PNG):

1. **Checkout practice**: v1 (placeholder labels, faint text, tiny link, five payment options), v2 (labels fixed, new colour only error), v3 (clean). Shows Compare and No issues found
2. **Sign up form**: one version with form problems and one pushback already written, so visitors see the "I disagreed" state
3. **Analytics dashboard**: one version with layout and hierarchy problems

Measured values in handwritten data must be real: compute them with the measuring code from docs/04 on the captured PNGs (run it in a script), never type numbers by hand.

## `pnpm demo:build` (live mode, run by the owner)

1. Capture all demo screens from the fixtures
2. Run the real pipeline on each (costs a few cents per screen)
3. Write `demo/data.json` with `source: "claude"` and the date
4. The owner reads the result, removes nothing silently, commits and redeploys

## Screens in demo mode (differences only)

* **Sidebar**: under the nav, a pill "Demo" and the source line, plus two text buttons: "How this demo works" (opens a dialog, below) and "Reset demo" (asks once, then clears `localStorage`)
* **Projects**: shows the sample projects; never the First use screen unless the visitor deleted everything (then First use with "Reset demo")
* **New review**: instead of the drop zone, a grid "Pick a sample screen" with the demo screenshots (thumbnail and name, each a radio card). Below it a note: "In the demo, reviews are prepared in advance. Run UX Critic on your own laptop with a Claude API key to review any screenshot." Project and version fields work as normal. Scale is fixed per sample. Start review shows the Reviewing screen with simulated step timing (about 6 seconds in total, instant with reduced motion), then the prepared review
* **Review, Compare, Project history**: identical. Push back reasons are saved in the browser
* **My checklist**: changes are saved in the browser. In demo they cannot change prepared reviews, so show a note: "In the demo, checklist changes apply to new reviews only." Connection section: "Demo mode · no API key needed"
* **Connect Claude, Review failed, Evaluation unreadable**: not reachable in the public demo. Add a hidden route `/states` (linked from "How this demo works") that shows these states with sample data, so visitors and interviewers can still see them

## Deployment (Vercel)

* Environment: `UXC_MODE=demo` only. No `ANTHROPIC_API_KEY`
* The build must not need SQLite or tesseract at runtime in demo mode
* `robots` allowed, `og:image` from a captured Review screen
* Playwright smoke test against the production build in demo mode: open every screen, axe on each
